GPU COMPUTE power profile — before/after, and the device-lost hangs
=====================================================================
Machine: RX 5600M (Navi 10, 6 GB) + Renoir iGPU, kernel 7.2.3, Ollama 0.33.3 Vulkan
Model: qwen3:4b-instruct-2507-q4_K_M, num_ctx 16384, ~4540-token prompt, no cache hit
(unique prefix per run). Applied by scripts/local-ai/setup-once.sh step 3.

Prefill throughput
  before (power_dpm_force_performance_level=auto)   ~79-84 tok/s   (2026-10-12-latency-profile.txt)
  after  (manual + COMPUTE profile)                 390-421 tok/s  (4 consecutive runs)
    num_batch 128: 390   512: 421   256: 413   512: 416   -> batch size doesn't matter
  first run right after applying the profile: 84 tok/s (clocks still ramping)
  generation: ~50-51 tok/s, unchanged

A ~4.5K-token first turn: ~55 s of prompt reading before -> ~11 s after.

Device-lost hangs (kernel: "ring comp_1.x.0 timeout", Ollama: vk::DeviceLostError)
  16:00:21, 16:03:01  sd-server Z-Image on the dGPU, profile NOT applied (auto) -> moved to iGPU
  18:37:48            first long prompt after setup-once.sh restarted Ollama, profile applied
  18:53:11            first long prompt after the dGPU had been idle (runtime-suspended, D3cold)
  After each: kernel ring reset succeeded, desktop unaffected (display is on the iGPU),
  Ollama respawned its runner; a short request right after worked.
  Then 6 long prompts in a row with the profile on: no hang.
Reading: hangs cluster on the first heavy request after a (re)start or wake.
Not proven whether the profile raises the odds. Mitigation in the app:
ollamaAdapter retries a runner crash (after 4 s, then 8 s) when nothing has been shown yet
(src/lib/providers/ollamaAdapter.ts, retryable()). If hangs keep happening, undo the
profile (setup-once.sh prints the undo line) and compare.

Embedder placement (found once background jobs could reach Ollama)
  nomic-embed-text loaded on the dGPU first -> qwen3:4b at 16K ctx (5.2 GB) got 35/37
  layers on GPU ("6%/94% CPU/GPU" in `ollama ps`) -> generation 17 tok/s instead of 51.
  Fix: embed requests send options.num_gpu=0 (CPU). CPU embed: 0.09 s/query, 2.5 s/32 texts.
  After: chat model 100% GPU, 51 tok/s.
  knowledge-extract  >150 s (gateway 504)  ->  66 s
  knowledge-lint      123 s                ->  63 s

Wake-from-suspend is the trigger (21:00-21:01)
  The dGPU runtime-suspends (D3cold) 5 s after each request even with a model "loaded"
  (VRAM evicted), so most chats begin with a full resume. Kernel log, wake -> hang:
    18:37:29 -> 18:37:48   18:52:53 -> 18:53:11   21:00:24 -> 21:00:42   21:01:12 -> 21:01:32
  4/4 hangs with the COMPUTE profile came 18-20 s after a resume. ~30 resumes before the
  profile: no chat hangs (the 16:00/16:03 ones were Z-Image on the dGPU).
  The app's immediate retry (6 s after) hit the dying runner and failed too.
Change: the card is held awake (power/control=on) with the profile only while the app
runs (cc-amdgpu-compute hold/release from local-up/local-down); stock otherwise. Retries
now wait 4 s, then 8 s. To verify after re-running setup-once.sh: chats after long idles.

ROOT CAUSE (21:09-21:26): prompt batch size, not the profile or the wake itself
  Since the 18:35 Ollama restart it ran the chat model with n_batch/n_ubatch 1024
  (512 in the morning's runs). Fresh model load + ~5K-token prompt:
    num_batch 1024 (Ollama's choice), stock settings, card asleep   3/3 device lost (20.6 s)
    1024, card held awake, fresh load                               1st fails, warm runner ok
    1024, fresh load, with a 1-token warm-up first                  4/5 device lost
    512, fresh load, card held                                      4/4 ok (15.5 s, faster)
    512, stock settings, card asleep                                3/3 ok (85 tok/s: low clocks)
    512 via the app (3 chats, model unloaded before each) + a background job: all ok
  Reading: one 1024-token GPU job on a just-loaded/just-woken card (low clocks) outruns
  the kernel's compute ring timeout -> reset -> ErrorDeviceLost. Fix: num_batch 512 in
  every request (ollamaConfig.ts OLLAMA_NUM_BATCH, ai-local.ts). Holding the card awake
  stays — it's for speed (330-415 vs 85 tok/s), not for stability.
